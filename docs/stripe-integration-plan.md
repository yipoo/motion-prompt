- Independent Supabase development project: `motion-prompt`, ref `ozzutjxoxdoqvxsfemmn`, Singapore, quoted $0/month at creation.
- Stripe sandbox: two Products, three approved Prices, a Customer Portal configuration, and 11 webhook event types configured. No live-mode keys or charges are enabled.

`tools/build-vercel.mjs` produces the Vercel Build Output API artifact: public static files and one bundled Node 24 billing function. Exported prompt/code URLs in the Vercel artifact point to Vercel. The original GitHub Pages export remains available. The account page is added only to Vercel; current free copy/install flows are preserved. Server credentials and billing source files never enter the static directory.

The backend no longer relies on a local SQLite database, a recurring timer, or work after an HTTP response. PostgreSQL stores durable state. Transaction-scoped advisory locks coordinate mutations across function instances. Webhooks are verified and processed before acknowledgment; failures return an error so Stripe can retry. Completed event IDs suppress duplicate deliveries. The SQLite store remains only as a local test/development adapter.

Database migration `billing/migrations/001_billing.sql` creates six tables in a private `motion_billing` schema. This migration has been applied to the new development project. RLS is enabled, with no browser access policies and schema/table access revoked for anonymous and authenticated client roles. Direct server database access is required. Use the Supabase transaction pooler with a suitable server credential; use certificate-verified TLS. Billing data must not be exposed through public tables or generic SQL RPCs.

Supabase client sign-in is implemented with email OTP/magic-link support and optional GitHub OAuth. The backend verifies Supabase JWT issuer, `authenticated` audience, signing key, expiry and subject. Public URL and publishable key are configured. Remaining account configuration: production SMTP, a suitable email template if using OTP, allowed callback URLs, and GitHub OAuth credentials before enabling that button.

`PREMIUM_CONTENT_READY=false` applies to the separate $9 design pack, which is not delivered yet. ## Payment and subscription flow

1. Configure sandbox Products and Prices in Stripe Dashboard: one Product per premium pack; one Pro Product with monthly/yearly Prices. Amounts and currency are business decisions, not example defaults.
2. Configure a server-only SKU → Price mapping. The server checks the Price is active and has the expected one-time/recurring type before Checkout.
3. Signed-in browser calls `POST /api/billing/checkout` with a catalog SKU and a stable `Idempotency-Key`. Reuse that key for transport retries. A deliberate new attempt gets a new key. Don't automatically generate new keys after an uncertain response.
4. Server creates a hosted Checkout Session using the mapped customer and price, dynamic payment methods, fixed return URLs, and English/Chinese locale. It rejects already-owned packs and duplicate/current/open Pro subscriptions. Successful checkout URLs are cached; unresolved attempts older than 23 hours require reconciliation.
5. The return page may show “confirming payment” and poll `/entitlements`. It must never unlock a pack by inspecting URL parameters or a success screen.
6. Webhooks verify the signature over the original raw bytes and retrieve current Stripe state inside a database transaction before acknowledging. Failures return an error and Stripe retries; duplicate deliveries are idempotent. Monitor failed Stripe deliveries and alert on persistent failures before live use.
7. `POST /portal` creates a portal session for the authenticated user's mapped customer only. Configure Portal in the sandbox before testing, including plan switching between the approved Pro prices.
8. `GET /invoices` returns only the signed-in customer's most recent 20 invoice records. Full invoice history is available in Portal. One-time invoices are enabled on Checkout; subscriptions use Billing invoices. Bespoke enterprise invoices can initially be drafted in Dashboard. An administrative invoice-send API is outside this starter.

## Webhooks and access rules

Register these snapshot events using the same pinned API version as the service (`2026-10-28.endive`):

```
checkout.session.completed
checkout.session.async_payment_succeeded
checkout.session.async_payment_failed
customer.subscription.created
customer.subscription.updated
customer.subscription.deleted
invoice.paid
invoice.payment_failed
charge.refunded
charge.dispute.created
radar.early_fraud_warning.created
```

Only a currently paid Checkout Session grants a one-time pack. Subscription access requires a configured Pro Price, current `active` status and an unexpired period. A cancellation scheduled for period-end remains active through that period; past-due, unpaid, canceled, expired and paused subscriptions do not grant Pro. This is a strict no-grace-period policy; confirm it before launch. Renewals and failures synchronize through the subscription and invoice events, using the invoice's `parent.subscription_details.subscription` relationship for the pinned API version.

Refunds (including partial refunds), disputes and early fraud signals place all paid access for the affected customer on hold. This intentionally conservative starter policy requires owner review; it does not automatically restore access when a case closes. Before production, choose a precise per-purchase refund policy, add an authenticated administrative review workflow with an audit trail, and reconcile against Stripe before removing a hold. No money is moved by this handler.

Private pack downloads go through the authenticated API. Do not put paid ZIP files in GitHub, `assets/`, `api/`, `studio/`, or any public CDN bucket. The current frontend content remains public and cannot be protected retroactively.

## Credentials, tax, and deployment

Use a separate Stripe sandbox and a restricted application API key with the minimal permissions required by Checkout, Customers, Prices, Subscriptions, Billing Portal, Invoices and read-only Charges. Configure the webhook signing secret independently. Store secrets in the deployment provider's secrets store; `.env` is for local development only, is ignored by Git, and is blocked by the development static server. Never supply server keys to `billing/client.mjs` or the static site. The starter rejects live keys and live webhook events. Local variables are synchronized to Vercel through stdin by `tools/sync-vercel-env.mjs`, without printing their values.

Tax is an unresolved launch requirement. Confirm the business's Stripe account country, customer markets, product tax codes, tax-inclusive/exclusive prices, and active registrations. Automatic tax is **not enabled** in this starter. Enabling it without active registrations does not mean tax will be collected. Once registrations and settings are confirmed, enable and test tax on Checkout and resulting invoices. Also confirm digital-content terms, refund policy, customer contact information and selling eligibility before live payments.

Operate the Vercel backend with ingress rate limits, managed Postgres backups and access controls, failed-delivery monitoring, reconciliation jobs, an error alert destination, and key rotation procedures. The in-process rate limiter is not a substitute for ingress protection. The database contains customer mappings and webhook event IDs: restrict access and define retention. Completed webhook payloads are cleared; Stripe retains failed deliveries for its retry process. The service is a **sandbox starter**, not a production-ready revenue system.
